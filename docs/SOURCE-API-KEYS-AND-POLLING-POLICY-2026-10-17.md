# Crypto — ключи API и политика частоты опроса

Дата: 2026-10-17  
Назначение: минимизировать лишние запросы, сохранять актуальность по требованиям конкретной метрики и не создавать ключи для ещё не выбранных/не принятых источников.

## 1. Общее правило частоты

**Целевой диапазон оперативных источников — 15–60 минут, только если данные действительно меняются с такой частотой и endpoint это поддерживает.** Это не глобальный таймер для всех источников.

- **15 минут** — только для оперативного spot price/market data, если это нужно потребителю и разрешено лимитами провайдера.
- **30 минут** — умеренно оперативные показатели, если более частое обновление не даёт существенной пользы.
- **60 минут** — стандартный режим для рыночных данных без доказанной потребности в 15/30 мин.
- **Daily / event-driven** — ETF daily flows/holdings, macro daily/session data, protocol releases, daily aggregates. Получать после обновления источника/публикации, а не повторять запрос каждые 15 минут.
- **Longer than daily / block-driven** — редкие или событийные показатели (например, difficulty, releases/vulnerabilities), по природе данных.
- Не запрашивать чаще, чем разрешает провайдер; учитывать rate limits, backoff при 403/429/5xx, cache headers, retry budget и стоимость.
- Частота опроса (`poll_interval`) отличается от допустимой свежести (`freshness_window`). Частота задаёт расписание запроса; freshness определяет, когда вход считается устаревшим. Нельзя улучшать freshness повторными запросами к источнику, который публикует данные раз в сутки.
- У каждого endpoint в будущем Source Catalog должны быть `poll_interval`, `poll_mode` (scheduled/event-driven/daily), `provider_min_interval`, `freshness_policy_id`, `rate_limit`, `backoff_policy` и дата последней проверки.

## 3. Предлагаемая частота по типу метрики

Это **стартовая политика**, а не подтверждение текущего автоматического расписания. Перед реализацией её нужно сопоставить с фактическими потребителями/сервисами и ограничениями каждого endpoint.

| Метрика / тип данных | Предлагаемый poll interval | Почему |
|---|---|---|
| BTC/USD spot (Kraken XBTUSD) | 15 мин при реальной потребности; иначе 30–60 мин | Сделки меняются непрерывно; metric freshness в registry сейчас 1h. Не запрашивать непрерывный поток, пока потребитель не требует его. |
| BTC/USDT cross-check (Binance data-api, OKX) | 30–60 мин | Независимая сверка, не канонический USD feed. |
| Mempool size | 15–30 мин только если используется для оперативного сигнала; иначе 1 ч | Быстро меняется, но частота должна соответствовать сценарию и rate limits. |
| Hashrate / block-fees aggregates | 1 ч или реже, по окну источника | Это агрегаты с периодом/окном; чаще опрашивать не значит получить новую независимую информацию. |
| Difficulty, circulating supply, UTXO, transactions/day, block time | 1 ч для обновления доступного состояния либо по событию/окну; daily aggregate — daily | Сохранять окно и единицы; не переинтерпретировать агрегаты как instant values. |
| ETF daily net flows / BTC holdings | Daily/event-driven после публикации; повторная сверка максимум по расписанию ревизий | SoSoValue и Farside показывают дневные значения; 15-минутный опрос создаст лишние запросы и не решит timestamp/finality. |
| Corporate BTC holdings | Daily/weekly или по факту публикации источника | Отчётность/обновления не являются 15-минутными данными. |
| Futures OI / funding / options OI | 15–60 мин только после выбора конкретного публичного endpoint и требований сценария | Сейчас `market.primary` — placeholder, поэтому точное расписание пока не утверждено. |
| DXY daily index / US 10Y yield | Daily/event-driven после сессии/публикации | Нужна семантика даты/времени и revision policy; 15–60 минут не подходят для daily series. |
| Core version / critical vulnerabilities | По релизу/публикации, плюс периодическая проверка не чаще необходимого | Событийные данные, не потоковый показатель. |

## 4. Ключи и секреты — правила безопасности

1. Значения ключей только в GitHub Actions Secrets или в будущем secret manager VPS; никогда не в Git, документации, логах, артефактах и Source Catalog.
2. В конфигурации хранить лишь ссылку, например `auth.secret_env: SOSOVALUE_API_KEY`.
3. Использовать ключи с минимальными read-only правами. Не создавать торговые/withdrawal keys для market-data задач.
4. Не добавлять ключ к endpoint, который работает публично, только «на всякий случай».
5. Не использовать ключи для обхода географических ограничений или условий использования.
6. Перед новым внешним подключением — сначала документация, тариф/ToS, лимиты, timestamps/revisions, права на хранение и архивирование; только потом секрет и интеграция.

## 5. Решение на текущий момент

- Уже нужен и настроен: `SOSOVALUE_API_KEY`, только для cross-check staging.
- Сейчас не требуется создавать другие ключи.
- Следующие ключи могут понадобиться после отдельного решения: Glassnode, выбранный derivatives provider, выбранный официальный macro source. DXY пока заблокирован; ключ не создавать.
- Следующий безопасный шаг — проверить реальные runtime call sites, согласовать polling interval с фактическими consumers, а затем вынести endpoint details/interval/rate-limit/secret reference в централизованный Source Catalog с тестами. Не менять canonical source priorities и не включать ingestion в рамках этого документационного шага.
