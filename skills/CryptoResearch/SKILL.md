# CryptoResearch v2

## Назначение

Универсальный skill для системного исследования криптоактивов и подготовки данных для постоянного мониторинга и публикации на сайте. Skill применяется к Bitcoin, Ethereum, Solana, NEAR и другим активам без изменения базовой методологии.

## Главный принцип

Исследование проходит последовательно:

**Задача → Исследование → Факты → Анализ → Результат → Мониторинг**

Нельзя смешивать проверяемые факты с интерпретациями. Для актуальных показателей всегда указывать дату или период данных.

## 1. Постановка задачи

Перед исследованием определить:

- какой актив исследуется;
- какой вопрос необходимо решить;
- на какую дату или период относится исследование;
- какие аспекты входят в область исследования;
- какой результат должен быть получен.

Если задача слишком широкая, декомпозировать её на отдельные исследовательские вопросы.

## 2. Декомпозиция

Использовать следующие блоки, адаптируя их к конкретному активу:

1. Суть проекта
2. Технология
3. Токеномика
4. Состояние сети
5. Экосистема
6. Пользователи и активность
7. Институциональное использование и капитал
8. Рынок
9. Макроэкономический контекст
10. Конкуренты
11. Риски
12. Катализаторы
13. Сценарии
14. Итог
15. Мониторинг

Не добавлять блок только ради полноты: каждый блок должен отвечать на конкретный исследовательский вопрос.

## 3. Источники

Приоритет:

1. первичные источники проекта и сети;
2. официальные документы и данные;
3. блокчейн-данные и специализированные аналитические платформы;
4. регуляторные и государственные источники;
5. качественные отраслевые исследования;
6. СМИ — преимущественно для событий и контекста.

Для важных утверждений использовать несколько независимых источников, когда это возможно.

## 4. Работа с данными

Для каждого существенного показателя фиксировать:

- значение;
- единицу измерения;
- дату или период;
- источник;
- при необходимости методику расчёта.

Не представлять устаревшие данные как текущие.

## 5. Классификация утверждений

Разделять:

**Факт** — непосредственно подтверждается источником.

**Расчёт** — получен математически из исходных данных.

**Анализ** — интерпретация подтверждённых фактов.

**Гипотеза** — возможное объяснение, которое требует дополнительной проверки.

Язык ответа должен показывать эту разницу.

## 6. Проверка противоречий

Если источники расходятся:

- не выбирать удобную цифру без объяснения;
- проверить даты и методики;
- определить, измеряют ли источники одно и то же;
- указать расхождение;
- при необходимости привести диапазон.

## 7. Анализ

После сбора фактов установить:

- основные изменения;
- причинно-следственные связи, если они подтверждаются;
- взаимосвязи между показателями;
- сильные и слабые стороны исследуемой системы;
- неизвестные и недостаточно подтверждённые области.

Не выдавать корреляцию за причинность.

## 8. Риски и катализаторы

Разделять:

- технологические;
- экономические;
- рыночные;
- регуляторные;
- инфраструктурные;
- экосистемные;
- конкурентные.

Для каждого существенного риска указывать механизм воздействия и что может служить ранним индикатором.

Для катализаторов указывать событие или условие и возможный канал воздействия, не выдавая сценарий за факт.

## 9. Сценарии

Сценарии должны описывать условия и возможные последствия.

Для каждого сценария:

- условия;
- ключевые подтверждающие индикаторы;
- возможные последствия;
- факторы, которые могут опровергнуть сценарий.

Не выдавать сценарии за прогнозы или гарантии.

## 10. Итог

Итог должен кратко отвечать:

1. Что мы установили?
2. Какие факты наиболее существенны?
3. Какие выводы следуют из анализа?
4. Что остаётся неизвестным?
5. Что необходимо отслеживать дальше?

Не использовать необоснованные рейтинги или итоговые оценки.

## 11. Мониторинг

Мониторинг является частью исследования, а не отдельным приложением к отчёту.

Для каждого мониторинга фиксировать:

- стабильный machine-readable ID показателя;
- название;
- значение;
- единицу измерения;
- дату/время observation;
- период, если показатель агрегированный;
- источник;
- методику расчёта;
- frequency обновления;
- freshness window — сколько времени значение считается актуальным;
- статус: NORMAL / WATCH / REVIEW;
- trigger — условие запуска нового исследования;
- связанные блоки исследования;
- confidence / качество источника, если это полезно.

### Принцип live-data

Skill не должен хранить текущие значения как единственный источник истины. Он определяет **что собирать, как проверять и как интерпретировать**. Текущие значения должны храниться отдельно в data layer проекта.

### Источник истины

Рекомендуемая цепочка:

**Primary source → ingestion → normalized observation → validation → snapshot/history → website API → website UI**

История наблюдений не должна перезаписываться текущим значением. Каждое обновление создаёт новую observation с timestamp и source.

### Правило обновления

Если источник изменил значение задним числом, не удалять старое observation. Добавлять новую запись с указанием периода/времени и, при необходимости, revision.

### Trigger policy

Если trigger сработал, не менять автоматически вывод исследования. Сначала создать событие мониторинга, затем выполнить повторную проверку источников и только после неё обновлять соответствующий research block.

**Дата исследования:** YYYY-MM-DD

## 13. Правило качества

Исследование считается завершённым только если:

- задача сформулирована;
- существенные блоки исследованы или явно отмечены как неприменимые;
- актуальность данных проверена;
- факты отделены от анализа;
- противоречия рассмотрены;
- риски и неизвестные обозначены;
- сформирован итог;
- определён мониторинг;
- ключевые источники зафиксированы.
